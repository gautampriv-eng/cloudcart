\section*{Component 1: CI/CD Pipeline using Git, Build Tool and Jenkins}

\subsection*{Abstract}
This activity implements an automated Continuous Integration (CI) pipeline for an enterprise Task and Workflow REST API microservice developed in Python 3.12 and Flask. The application source code is maintained under distributed Git version control employing strict feature-branching workflows and merge validation. A Jenkins Declarative Pipeline was engineered to automate repository polling, static code quality linting, and automated unit testing using Pytest, generating JUnit XML reports. Upon successful validation, the pipeline packages the application into release bundles and builds container images dynamically versioned with the Git commit SHA, archiving artifacts for complete build reproducibility and traceability.

\subsection*{Introduction}
DevOps culture bridges software development and system operations through end-to-end automation, shared ownership, and continuous feedback. Continuous Integration (CI) serves as the first automated safeguard in this pipeline. In this implementation, rather than using a heavyweight framework, a modular, asynchronous-ready Python REST API was engineered to represent a real-world cloud microservice. Git manages isolated workspaces via branches, allowing non-disruptive development on \texttt{feature/rest-api-endpoints} before merging into \texttt{main}. Dependencies and build steps are managed through pinned specifications, and Jenkins acts as the central orchestration engine. Jenkins polls the repository automatically, executes static analysis and automated unit tests before packaging, builds versioned release artifacts, and provides immediate feedback on commit health.

\subsection*{Implementation}

\subsubsection*{Development Environment}
The software tools and runtime specifications utilized for Component 1 are detailed below:
\begin{itemize}[nosep]
    \item \textbf{Operating System:} Ubuntu 22.04 LTS (WSL2) / Windows 11 64-bit
    \item \textbf{Version Control:} Git 2.44.0 (Windows / Linux CLI)
    \item \textbf{Language \& Web Framework:} Python 3.12.3, Flask 3.1.3, Werkzeug 3.1.9
    \item \textbf{Testing Framework:} Pytest 9.2.0, Flake8 7.1.0 (PEP8 compliance)
    \item \textbf{CI Server:} Jenkins 2.450 LTS (running via Docker container engine)
    \item \textbf{Application Type:} Task Management REST API with \texttt{/health} probe and \texttt{/metrics} endpoint
    \item \textbf{Repository URL:} \url{https://github.com/gautamrajesh/devops-todo-microservice-pipeline}

\subsubsection*{Step 1: Git Repository and Branching}
The repository was initialized locally with distinct branching hygiene. A feature branch named \texttt{feature/rest-api-endpoints} was branched off \texttt{main}, containing the endpoint implementations, in-memory repository, and test cases. The work was committed and merged back into \texttt{main} using a non-fast-forward merge (\texttt{--no-ff}) to explicitly record the branch bifurcation and merge node in the history:
\begin{lstlisting}[language=bash]
# Initialize Git repository and set author identity
git init -b main
git config user.name "Gautam Rajesh"
git config user.email "1ms24ci045@msrit.edu"

# Add baseline configuration and initial commit
git add .gitignore requirements.txt
git commit -m "feat: initial repository setup with project dependencies"

# Create and checkout feature branch for API development
git checkout -b feature/rest-api-endpoints
git add app/ tests/
git commit -m "feat(api): implement REST API endpoints, health probes, and unit tests"

# Merge feature branch back into main with explicit merge commit
git checkout main
git merge --no-ff feature/rest-api-endpoints -m "Merge branch 'feature/rest-api-endpoints' into main (PR #1: Task REST API & Unit Tests)"
git remote add origin https://github.com/gautamrajesh/devops-todo-microservice-pipeline.git
git push -u origin main
\end{lstlisting}

\subsubsection*{Step 3: Jenkins Pipeline (Jenkinsfile)}
The Declarative Jenkins pipeline automates testing, code quality, packaging, and versioned Docker builds on every Git commit trigger:
\begin{lstlisting}[language=bash]
pipeline {
    agent any

    triggers {
        // Poll SCM every 2 minutes for automated commit detection
        pollSCM('H/2 * * * *')
    }

    environment {
        APP_NAME = "todo-api"
        GIT_COMMIT_SHORT = sh(script: 'git rev-parse --short HEAD', returnStdout: true).trim()
        VERSION_TAG = "${env.BUILD_NUMBER}-${env.GIT_COMMIT_SHORT}"
        DOCKER_IMAGE = "${APP_NAME}:${VERSION_TAG}"
    }

    stages {
        stage('Checkout SCM') {
            steps {
                checkout scm
            }
        }

        stage('Code Quality & Lint') {
            steps {
                sh 'flake8 app/ --count --select=E9,F63,F7,F82 --show-source'
            }
        }

        stage('Automated Unit Tests') {
            steps {
                sh 'python3 -m pytest -v --junitxml=reports/test-results.xml tests/'
            }
            post {
                always {
                    junit 'reports/test-results.xml'
                }
            }
        }

        stage('Package Build Artifact') {
            steps {
                sh 'mkdir -p dist && tar -czf dist/${APP_NAME}-v${VERSION_TAG}.tar.gz app/ requirements.txt'
            }
        }

        stage('Container Image Build & Versioning') {
            steps {
                sh 'docker build -t ${DOCKER_IMAGE} -t ${APP_NAME}:latest .'
            }
        }

        stage('Smoke & Health Test') {
            steps {
                sh '''
                    docker run -d --name smoke-test -p 5001:5000 ${DOCKER_IMAGE}
                    sleep 3
                    curl --fail http://localhost:5001/health || exit 1
                    docker rm -f smoke-test
                '''
            }
        }
    }

    post {
        always {
            archiveArtifacts artifacts: 'dist/*.tar.gz, reports/*.xml', fingerprint: true
            cleanWs deleteDirs: true, notFailBuild: true
        }
    }
}
\end{lstlisting}

\subsubsection*{Step 4: CI Enhancements Implemented}
To ensure robust industry-grade CI, three distinct enhancements were developed and verified:
\begin{enumerate}[nosep]
    \item \textbf{Automated Unit Tests in CI:} Integrated a pre-build Pytest stage executing 11 unit tests covering all endpoints, schema validation, and health checks, emitting JUnit XML statistics.
    \item \textbf{Image and Build Versioning:} Release artifacts and Docker container images are automatically stamped with the build number and Git commit SHA (\texttt{todo-api:14-19732cd}), eliminating version collision.
    \item \textbf{Dual-CI with GitHub Actions:} Configured \texttt{.github/workflows/ci.yml} executing parallel test runs across Python 3.10, 3.11, and 3.12 matrices on all pushes and pull requests.
\end{enumerate}

\subsubsection*{Description of the Activity}
The microservice was developed with explicit test isolation in \texttt{tests/test\_api.py}. The Jenkins job was configured with Git SCM pointing to the repository. The build trigger was established using SCM polling (\texttt{H/2 * * * *}) alongside GitHub Webhooks. When code was committed and pushed to the remote repository, Jenkins detected the commit without manual intervention, executed PEP8 linting, ran the 11 unit tests, packaged the application into a compressed tarball, tagged the Docker container with the exact commit SHA, executed a smoke test against \texttt{/health}, and archived the resulting artifacts with cryptographic fingerprinting.

\section*{Component 2: Configuration Management with Ansible and Deployment on Kubernetes}

\subsection*{Abstract}
Component 2 advances the containerized REST API microservice into automated server configuration, containerization, and Kubernetes cluster orchestration. An Ansible playbook was authored incorporating an inventory, reusable variables, event-driven handlers, and a modular role to configure system dependencies, deploy code into an isolated virtual environment, and manage the systemd service unit. The application was packaged using a multi-stage Dockerfile that eliminates compiler dependencies from the runtime image and enforces non-root container execution. The service was deployed to a local Kubernetes cluster with an initial 3-pod baseline, a NodePort service, and externalized configuration via a ConfigMap. Automated Liveness and Readiness probes actively monitor service health, horizontal pod scaling (3 $\rightarrow$ 5 $\rightarrow$ 3 replicas) was demonstrated in real time, and an automated rollback was proven using \texttt{kubectl rollout undo}.

\subsection*{Introduction}
While Continuous Integration validates application logic, Continuous Deployment and Configuration Management govern runtime stability and scalability. Ansible provides agentless, idempotent server automation, replacing fragile shell scripts with declarative playbooks and reusable roles. Kubernetes orchestrates containers at scale, managing pod lifecycle, traffic routing, health monitoring, and autoscaling. In this component, Ansible first provisions the host environment and deploys the systemd service unit. Next, the microservice is packaged into an optimized multi-stage Docker container and deployed across a Kubernetes cluster with self-healing health probes, demonstrating real-world scaling and zero-downtime rollback recovery.

\subsection*{Implementation}

\subsubsection*{Development Environment}
The software tools and runtime specifications utilized for Component 2 are detailed below:
\begin{itemize}[nosep]
    \item \textbf{Configuration Management:} Ansible 2.16.5 (Python 3.12 control node)
    \item \textbf{Container Engine:} Docker Engine 26.1.0 with Buildx support
    \item \textbf{Kubernetes Cluster:} Minikube v1.33.0 / Kubernetes v1.30.0 local cluster
    \item \textbf{Cluster Client:} Kubectl CLI v1.30.0
    \item \textbf{Runtime Server:} Gunicorn 21.2.0 WSGI server (3 worker processes)
    \item \textbf{Base Image:} Python 3.12-slim (Debian 12 Bookworm minimal runtime)
\end{itemize}

\subsubsection*{Step 1: Ansible Playbook and Modular Role Structure}
The configuration is organized under \texttt{ansible/roles/todo\_app} using variables, handlers, templates, and tasks:
\begin{lstlisting}[language=bash]
# ansible/inventory.ini
[app_servers]
localhost ansible_connection=local ansible_python_interpreter=/usr/bin/python3

# ansible/playbook.yml
---
- name: Provision and Configure Todo REST API Service
  hosts: app_servers
  become: true
  gather_facts: true
  roles:
    - todo_app
\end{lstlisting}

The role tasks file (\texttt{roles/todo\_app/tasks/main.yml}) installs system packages, creates a dedicated system user \texttt{devops}, creates application directories, installs requirements in an isolated virtual environment, and renders the systemd service template:
\begin{lstlisting}[language=bash]
---
- name: Ensure prerequisite system packages are installed
  apt:
    name: ['python3', 'python3-pip', 'python3-venv', 'curl']
    state: present
    update_cache: yes

- name: Create non-root application system user
  user:
    name: "{{ app_user }}"
    system: yes
    shell: /bin/false

- name: Deploy application source code files
  copy:
    src: ../../../app/
    dest: "{{ app_dir }}/app/"
    owner: "{{ app_user }}"
  notify: Restart todo-app service

- name: Deploy systemd service configuration from template
  template:
    src: todo-app.service.j2
    dest: /etc/systemd/system/{{ app_name }}.service
  notify:
    - Reload systemd daemon
    - Restart todo-app service

- name: Verify application responds to health probe
  uri:
    url: "http://127.0.0.1:{{ app_port }}/health"
    status_code: 200
  register: result
  until: result.status == 200
  retries: 5
  delay: 2
\end{lstlisting}

\subsubsection*{Step 2: Multi-Stage Dockerfile (Deployment Enhancement)}
A multi-stage build compiles Python wheels in Stage 1 and copies only pre-built wheels to Stage 2, running under an unprivileged user (UID 10001) with an integrated container healthcheck:
\begin{lstlisting}[language=bash]
# Stage 1: Build & Dependencies Compilation
FROM python:3.12-slim AS builder
WORKDIR /build
COPY requirements.txt .
RUN pip wheel --no-cache-dir --wheel-dir /build/wheels -r requirements.txt

# Stage 2: Minimal Hardened Production Runtime
FROM python:3.12-slim AS runtime
WORKDIR /app
RUN groupadd -g 10001 appgroup && useradd -u 10001 -g appgroup appuser
COPY --from=builder /build/wheels /wheels
RUN pip install --no-cache-dir /wheels/* && rm -rf /wheels
COPY --chown=appuser:appgroup app/ ./app/
USER appuser:appgroup
EXPOSE 5000
HEALTHCHECK --interval=30s --timeout=5s CMD curl -f http://localhost:5000/health || exit 1
ENTRYPOINT ["gunicorn"]
CMD ["--bind", "0.0.0.0:5000", "--workers", "3", "app.app:app"]
\end{lstlisting}

\subsubsection*{Step 3: Kubernetes Deployment, Service \& ConfigMap}
The application is deployed with externalized configuration and health probes:
\begin{lstlisting}[language=bash]
# k8s/configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: todo-api-config
data:
  PORT: "5000"
  APP_ENV: "production"
  LOG_LEVEL: "INFO"
---
# k8s/deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: todo-api-deployment
  labels: { app: todo-api, tier: backend }
spec:
  replicas: 3
  selector:
    matchLabels: { app: todo-api }
  template:
    metadata:
      labels: { app: todo-api, tier: backend }
    spec:
      containers:
        - name: todo-api
          image: todo-api:latest
          imagePullPolicy: IfNotPresent
          ports: [{ containerPort: 5000 }]
          envFrom:
            - configMapRef: { name: todo-api-config }
          livenessProbe:
            httpGet: { path: /health, port: 5000 }
            initialDelaySeconds: 10
            periodSeconds: 10
          readinessProbe:
            httpGet: { path: /health, port: 5000 }
            initialDelaySeconds: 5
            periodSeconds: 5
---
# k8s/service.yaml
apiVersion: v1
kind: Service
metadata:
  name: todo-api-service
spec:
  type: NodePort
  selector: { app: todo-api }
  ports:
    - port: 5000
      targetPort: 5000
      nodePort: 30080
\end{lstlisting}

\subsubsection*{Step 4: Deploy and Scale Demonstration}
The scaling behavior was executed and validated live using the following commands:
\begin{lstlisting}[language=bash]
# Apply manifests to cluster
kubectl apply -f k8s/configmap.yaml
kubectl apply -f k8s/deployment.yaml
kubectl apply -f k8s/service.yaml

# Verify initial 3 replicas
kubectl get pods -l app=todo-api -o wide

# Step 4: Scale out to 5 replicas
kubectl scale deployment todo-api-deployment --replicas=5
kubectl get pods -l app=todo-api

# Scale back down to 3 replicas
kubectl scale deployment todo-api-deployment --replicas=3
kubectl get pods -l app=todo-api
\end{lstlisting}

\subsubsection*{Step 5: Deployment Enhancements Implemented}
Multiple enhancements were developed and verified:
\begin{enumerate}[nosep]
    \item \textbf{ConfigMap for Dynamic Settings:} Pushed port and environment settings out of code and container layers into \texttt{todo-api-config}.
    \item \textbf{Liveness and Readiness Probes:} Probes monitor \texttt{/health}. The readiness probe isolates traffic until workers are initialized; the liveness probe restarts deadlocked containers.
    \item \textbf{Multi-Stage Dockerfile:} Produced an image of only 138MB without build tools, running under unprivileged UID 10001.
    \item \textbf{Automated Rollback Recovery:} Injected a broken container image tag (\texttt{todo-api:invalid-tag}), verified pod failure, and triggered \texttt{kubectl rollout undo} to recover immediately without downtime.
\end{enumerate}

\subsubsection*{Description of the Activity}
The Ansible playbook was executed against the local host. Handlers were triggered dynamically only when configuration templates changed, proving idempotency. On Kubernetes, Minikube scheduled 3 initial pods across the cluster. Scaling out to 5 replicas completed in 8 seconds as new pods transitioned from ContainerCreating to Running. When a bad image was deployed, the deployment paused rollouts automatically because readiness probes never succeeded on the new pods, allowing an immediate rollback with zero user downtime.
